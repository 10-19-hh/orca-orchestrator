# Orca Orchestrator

PRD의 요구사항을 검증 가능한 개발 작업으로 나누고, Orca를 통해 Claude Code와 Codex에 배정하기 위한 Python 프로젝트입니다. 작업 결과와 테스트를 요구사항에 연결하고, 최종 변경은 사용자가 승인하는 흐름을 목표로 합니다.

> **현재 Worker 작업 전송은 보류 상태입니다.** 이 버전은 Orca 상태를 읽어 보여주고 Worker 명령을 보내기 직전까지만 점검하며, Worker를 시작하거나 모델에 작업을 보내지 않습니다.

## 한눈에 보기

- **Orca 터미널 안의 TUI:** Orca 터미널 탭에서 `python -m orca_orchestrator`를 실행하면 작업 목록·상세·변경 검토·복구·전송 전 점검 탭과 확인 대화상자를 갖춘 대화형 TUI가 그 터미널 안에서 열립니다. 작업을 골라 로컬 검증을 실행하고, 흐름을 시작·이어가고, 변경을 검토해 승인·보류하고, 실행 없는 전송 전 점검을 볼 수 있습니다. 브라우저·웹 서버·별도 앱은 없고 Worker도 시작하지 않습니다. [대화형 TUI](#대화형-tui)
- **Orca 터미널에서 보이는 것:** Orca 터미널 탭에서 `python -m orca_orchestrator`를 실행하면 Runtime 연결·버전, Coordinator 바인딩, 현재 Run, 작업 전송 보류 이유, 사용량(`미확인`)이 한 화면에 나옵니다. `--tasks`로 작업 정의 파일을 지정하면 작업별 상태, 요구사항 충족 여부, 다음 작업, 흐름이 멈춘 이유와 함께 **어떤 코드를 검증했는지, 기준 버전 대비 변경 파일이 어느 작업에 속하는지, 무엇이 승인을 막는지**가 나옵니다. 아래 텍스트 화면(`--once`, `--plain`)은 읽기 전용입니다.
- **로컬 검증부터 승인까지:** `flow`가 작업을 골라 단위 테스트로 검증하고, `review`로 변경과 증거를 확인한 뒤 사용자가 `--approve`로 직접 승인합니다. 승인 후 코드나 작업 정의가 바뀌면 화면에 `재승인 필요`가 표시됩니다. 자동 승인은 없습니다. [예제로 따라 하기](#로컬-검증부터-승인까지)
- **중단과 이어받기:** 작업마다 실행 기록을 남겨, 새 세션이 `handoff`로 어디까지 했고 무엇이 남았는지와 다음 행동을 확인한 뒤 `flow`로 직접 이어갑니다. 끝났는지 모르는 실행이나 다른 세션이 잡고 있는 작업은 다시 실행하지 않습니다. [예제로 따라 하기](#중단과-이어받기)
- **Worker 전송 전 점검:** `python -m orca_orchestrator.preflight`가 예정 Provider, Coordinator 바인딩, Run과 보낼 작업, 그대로 보낼 `worker-start` 명령, Worker 명령의 근거 수준, 필요한 승인과 차단 사유를 보여줍니다. Run을 만들거나 Worker를 기동하거나 작업을 보내지 않습니다. [예제로 따라 하기](#worker-전송-전-점검)
- **Orca 없이 데모 열기:** 저장소 루트의 PowerShell에서 아래 두 줄을 실행합니다. 포함된 응답 픽스처만 재생하므로 Orca가 꺼져 있어도 열리고 실제 CLI는 호출하지 않습니다.

```powershell
$env:PYTHONPATH = "src;tests"
python -m orca_orchestrator --demo
```

## 지금 써볼 수 있는 범위

`Python 제어 코드 → Orca CLI 어댑터 → Orca Runtime`

- **Orca 어댑터**는 Runtime 상태와 현재 Run을 조회하고, Orca 터미널 바인딩이 있는 경우 Run을 생성할 수 있습니다. Experiment 1은 Orca `1.4.264`에서 `COORDINATOR`의 Run 생성과 바인딩을 확인했습니다. Run은 실행 컨텍스트이며 생성만으로 Worker가 시작되지는 않습니다. Worker Dispatch의 상태는 `worker-show`로 읽습니다. 간략 `--json` 응답의 필드는 설치된 `1.4.264` CLI 기준이고, 상태 값과 그 순서는 Experiment 4-B에서 Claude Worker 한 번으로 관측했습니다.
- **Worker 어댑터와 전송 전 점검**은 설치된 Orca `1.4.264`의 명령 스키마와 릴리스 소스에 맞춰 `worker-start` 명령을 구성하고 응답을 해석합니다. 구성한 명령은 `preflight`로 확인만 할 수 있고, 이 빌드에는 보내는 경로가 없습니다. Worker 실행 ID와 상태는 실행 기록에 연결해 재전송과 재배정을 막는 데 씁니다. 4-B에서 관측한 대로 작업 완료, 터미널 정리, 프로세스 종료를 따로 판정합니다(가짜 실행기로 검증).
- **읽기 전용 상태 화면**은 Runtime 연결·버전, Coordinator 바인딩, 현재 Run, 작업 전송 보류 이유를 한 화면에 보여줍니다. Orca 상태를 바꾸지 않습니다.
- **대화형 TUI**는 같은 상태를 Orca 터미널 탭 안의 패널로 보여 주고, 선택한 작업의 로컬 검증, 흐름 시작·이어가기, 변경 검토와 최종 승인·보류, 실행 없는 전송 전 점검을 확인 대화상자를 거쳐 실행합니다. 판정과 기록은 기존 로직과 파일 형식을 그대로 씁니다.
- **작업 목록**은 직접 정의한 작업에 요구사항 ID, 작업 ID, 선행 작업, 검증 조건을 연결합니다. 중복 ID, 없는 선행 작업, 순환 의존성을 오류로 표시하고, 입력된 검증 결과로 작업 상태와 요구사항 충족 여부를 판정합니다.
- **로컬 검증**은 사용자가 직접 호출할 때 `unit-tests` 검증 조건으로 저장소 단위 테스트를 한 번 실행하고, 종료 코드로 통과·실패를 결과 파일에 기록합니다.
- **로컬 검증 흐름**은 다음 작업을 결정적으로 골라 하나씩 검증하고, 실패·미완료·기록 실패에서 멈추며, 저장된 결과에서 이어갑니다. 요구사항 → 작업 → 검증 조건 → 실행 결과를 추적해 보여줍니다.
- **변경 검토와 최종 승인**은 검증 결과가 현재 코드(커밋 전 변경 포함)에 맞는지, 작업 정의의 기준 버전 대비 어떤 파일이 바뀌었고 어느 작업에 속하는지, 보호 경로가 바뀌지 않았는지 확인합니다. 승인과 보류는 사용자가 `review` 명령이나 TUI의 승인·보류 대화상자로만 기록합니다.
- **인수인계와 중단 후 복구**는 작업을 시작할 때 범위·기준 버전·코드 기준·실행 ID를, 끝나거나 멈출 때 완료한 확인·남은 확인·중단 이유·다음 행동을 기록합니다. 재개 전에 이 기록을 현재 작업 정의·코드·결과와 대조하고, 끝났는지 모르는 실행과 다른 세션이 실행 중인 작업은 다시 실행하지 않습니다.
- **작업 전송 게이트**는 연결·버전·바인딩·승인·과금 조건과 사용량 대기 상태를 평가합니다. 현재 빌드는 Worker를 시작하거나 작업을 보내지 않습니다.
- **개발 예정**은 실제 Worker 전송(4-A 통과와 별도 사용자 승인 뒤)과 실환경 상태 제어, 사용량 연동, PRD 문서에서 작업 추출, 단위 테스트 외 검증, 교차 리뷰 증거 연결, 승인 후 병합 연동입니다.

## 로컬 시작

Python 3.11 이상이 필요합니다. Windows PowerShell에서 저장소 루트 기준으로 소스를 불러올 수 있습니다. 이 방식은 패키지 설치나 Orca 연결 없이 실행됩니다. 핵심 기능과 텍스트 화면의 런타임 Python 의존성은 없습니다. 대화형 TUI만 선택 의존성 Textual을 씁니다([설치와 실행](#설치와-실행)).

```powershell
$env:PYTHONPATH = "src;tests"
python -c "from orca_orchestrator.orca import OrcaCliAdapter, WorkDispatcher"
```

로컬 테스트도 같은 셸에서 실행합니다.

```powershell
python -m unittest discover -s tests -v
```

테스트는 가짜 Orca 명령 실행기와 응답 픽스처를 사용합니다. Worker 시작 응답의 타입·Dispatch·Run 일치, 작업 정산과 터미널 정리 및 종료의 구분, 조회 실패 후 마지막 확인 상태 보존, 미확인 실행 재전송 차단을 검증합니다. 출력의 완료 문구나 사용량 표시만으로 성공·과금을 판정하지 않습니다.

Textual 헤드리스 테스트는 Console의 검증·흐름·승인·보류, 조회 실패와 지연, 픽셀 마당의 상태 표시·입력·애니메이션을 검증합니다. Textual이 없으면 화면 테스트를 건너뜁니다. 그 밖의 테스트는 명령 구성과 전송 차단, 작업·검증 결과 판정, 코드 지문·변경 검토, 승인·복구, Snapshot v1 출력을 확인합니다. 실행기와 세션 테스트는 로컬 Python 서브프로세스와 임시 Git 저장소를 사용합니다. Orca나 모델은 호출하지 않습니다.

## 대화형 TUI

Orca 터미널 탭에서 `python -m orca_orchestrator`를 대화형 터미널로 실행하면 TUI가 **그 터미널 안에서** 열립니다. 기본 화면은 Codex 펫과 Claude 펫이 뛰어다니는 [픽셀 마당](#픽셀-마당-기본-화면)이고, 작업·변경 검토·복구·전송 전 점검은 마당에서 여는 [상세 콘솔](#화면)(패널·작업 선택·확인 대화상자)에 있습니다. `--console`로 상세 콘솔을 바로 열 수 있습니다. 브라우저, 웹 서버, 별도 앱은 없고 Orca를 수정하지 않습니다. 완료·요구사항 충족·재개·승인 가능 여부는 기존 판정 결과를 그대로 보여 주며, 동작은 `verify`·`flow`·`review`·`preflight` 명령과 같은 함수를 호출합니다. Worker를 시작하거나 모델에 작업을 보내는 동작은 없습니다.

### 설치와 실행

TUI에는 [Textual](https://textual.textualize.io/) `>=8.2.8,<9`가 필요합니다(선택 의존성 `tui`). 핵심 기능, `--once` 출력, 기존 텍스트 화면은 여전히 표준 라이브러리만 씁니다. 아래 macOS·Linux 명령은 macOS에서 Python 3.11·3.12로 확인했습니다. Windows에서는 Python 3.11 가상환경으로 헤드리스 테스트와 CLI 데모를 확인했습니다. 실제 Windows Orca 탭의 대화형 동작은 미확인입니다.

```bash
# macOS·Linux, 저장소 루트
python3 -m venv .venv
.venv/bin/python -m pip install -e ".[tui]"
.venv/bin/python -m orca_orchestrator --demo                       # 데모 (Orca 호출 없음)
.venv/bin/python -m orca_orchestrator --tasks plan.json --results results.json --repo .
```

```powershell
# Windows PowerShell, 저장소 루트 (기존 방식처럼 소스를 직접 불러올 때)
```

- 기본은 픽셀 마당입니다. `--console`은 마당 없이 기존 탭 콘솔(작업·변경 검토·복구·전송 전 점검)을 바로 엽니다. `--motion normal|reduced|off`는 마당의 움직임을 정합니다(기본 `normal`).
- 대화형 터미널이 아니거나(파이프·리디렉션) `--once`를 주면 기존 텍스트 화면을 출력합니다. `--plain`은 기존 읽기 전용 화면(`r`·`q`)을 엽니다.
- Textual이 없으면 설치 방법을 한 줄 알리고 기존 읽기 전용 화면을 엽니다. 다른 명령(`verify`, `flow`, `review`, `handoff`, `preflight`)은 Textual과 무관합니다.
- `--demo`, `--demo-results`, `--tasks`, `--results`, `--repo`는 기존과 같습니다. `--timeout`은 TUI에서 실행하는 검증 하나의 제한 시간입니다(기본 600초).
- Coordinator 바인딩은 Orca 터미널이 넘겨준 `ORCA_TERMINAL_HANDLE`을 그대로 씁니다. 핸들을 만들거나 입력받지 않습니다. 바인딩이 없으면 로컬 작업·검증·검토 정보는 그대로 보여 주고 Run 조회와 그 이유만 표시합니다.

### 픽셀 마당 (기본 화면)

어두운 방을 비스듬히 내려다보는 2.5D 화면입니다. 뒤쪽 벽에는 밤하늘 창문과 화분이 있고, 다이아몬드 타일 바닥에는 러그와 책상이 놓여 있습니다. 작은 Codex 펫(파란 구름 머리 로봇, 화면에 `>_`)과 Claude 펫(주황 크리터)은 바닥을 앞뒤·좌우로 돌아다닙니다. 발 위치 순서로 그려지므로 책상 앞에 선 펫은 책상을 가리고, 뒤에 선 펫은 가려집니다. 바닥에는 그림자가 생깁니다. 이 화면에서 **로컬 검증이 실제로 시작되면** 둘이 책상 양옆으로 달려가 켜진 모니터를 지켜봅니다. 로컬 검증은 펫이 하는 일이 아니므로 타이핑·망치질은 하지 않습니다(그 동작은 해당 에이전트의 Worker가 관측될 때를 위해 남겨 두었고, 이 빌드는 Worker를 관측하지 않습니다). 확인할 일이 생기면 Codex 펫 위에 말풍선이 뜹니다. 긴 설명·로그·정책 근거는 이 화면에 두지 않고, 펫·책상·말풍선·요청을 고르면 해당 상세 화면이 열립니다.

실제 마당은 위 상자 안을 `▀`·`▄`·`█` 반블록과 색으로 그린 그림입니다(위는 구조 설명용 스케치).

- **헤더:** 프로젝트(저장소), 데모 여부(`모의 상태 · 실제 CLI·실행·기록 없음`), Runtime 연결·바인딩, Worker 전송 차단, 마지막 조회 시각과 `최신 아님`.
- **펫의 동작은 기존 판정을 따릅니다.** 대기·준비(`▸ 준비 · 실행 시작 아님`)에는 돌아다니다가 멈춰서 쉬거나 눈을 깜빡이고, 빗자루질을 하거나 생각 말풍선(점 세 개)을 띄웁니다. 조회 전에는 생각 중, 한도 대기(전송 게이트가 판단한 경우만)에는 `z`를 띄우고 잡니다. 이 화면에서 로컬 검증 시작 이벤트가 오면 책상으로 급히 달려가 모니터를 지켜봅니다(타이핑·망치질 없음). 실행 기록상 다른 세션이 작업을 실행 중이면 책상으로 가지 않고 제자리에서 기다리며, 누가 실행하는지는 추정하지 않습니다(상세에서 확인). 검증 실패에는 Codex 펫 화면에 `x x`가 뜨고 Claude 펫은 쓰러집니다. 종료 미확인과 Worker 터미널 정리 중에는 `?`를 띄우고 제자리에서 기다립니다. 정리 중 상태에는 복구 탭에서 읽기 전용으로 다시 조회할 수 있다는 안내가 나옵니다. 변경 검토가 필요하면 Codex 펫이 `!`를 띄우고, 검증 통과에는 반짝이며 기뻐합니다. `준비`나 작업 발견만으로는 달려가지 않고, 달려가는 중에 실행이 끝나면 도착을 기다리지 않고 바로 새 상태를 보여 줍니다. **펫은 마스코트이지 Worker가 아닙니다.** 책상에서 지켜보는 동작은 항상 `로컬 검증 … Worker 아님`으로 표시되며, 이 빌드는 Claude·Codex에 작업을 보내지 않습니다.
- **상태 줄:** 기호와 글자로 상태를 씁니다(`⚙ 로컬 검증 실행 중`, `✗ 검증 실패`, `? 종료 미확인`, `✓ 검증 통과 · 최종 승인 아님`, `✓ 사용자 최종 승인됨` 등). 검증 통과와 최종 승인은 다른 줄로 표시하고, Worker 전송 차단은 실패로 표시하지 않습니다. 사용량은 연동 전이라 대기·리셋 시각·진행률을 만들어 보여 주지 않습니다.
- **말풍선과 요청함:** 요청은 기존 판정에서 만듭니다(종료 미확인, 실행 기록 읽기 불가, 작업 정의 오류, 검증 실패, 필요한 검증 결과 없음·재확인, 보호 경로 변경, 변경 비교 불가, 연결 없는 변경, 최종 승인·재승인 필요). 같은 대상·종류는 하나로 묶여 새로고침해도 늘지 않고, 요청함에는 모두, 말풍선에는 가장 급한 안 읽은 요청 하나가 나옵니다. 말풍선을 닫거나(`d`) 열어 본 요청은 `읽음`일 뿐 해결이 아니며 요청함에 남습니다. 근거가 사라질 때(다시 조회한 결과)만 없어지고, 다시 실행하면 현재 파일에서 미해결 요청을 다시 만듭니다.
- **클릭은 상세만 엽니다.** 펫·작업대는 연결된 작업의 상세(작업 탭), 말풍선·요청은 근거가 있는 탭(종료 미확인은 복구, 승인·변경은 변경 검토, 실패는 작업)을 엽니다. 검증·흐름·승인·보류는 상세 화면의 기존 확인 대화상자로만 실행·기록됩니다. 마당에서는 `v`·`s`·`a`·`h`·`p` 같은 키가 동작하지 않습니다.
- **상세에서 돌아오기:** 마당에서 연 상세는 `Esc`로 마당에 돌아오고, 마당의 선택(펫·작업대·말풍선)과 포커스(마당·요청함)가 그대로입니다. 상세 콘솔에서는 `y`로도 마당에 돌아옵니다.
- **애니메이션은 표시만 합니다.** 최대 8fps이며 프레임 타이머는 펫 위치와 그림만 바꿉니다. 조회·Git·Orca·검증·Worker 호출은 기존 새로고침(`r`)과 실행 이벤트에서만 일어납니다. 마당이 상세 화면 뒤에 가려졌거나 앱이 비활성이면 타이머를 멈춥니다.
- **좁은 화면:** 폭 70칸 또는 높이 22줄보다 작으면 펫을 정지 그림으로 두고 요청함 아래에 작업 목록을 함께 보여 줍니다. 크기를 바꾸면 펫·작업대·말풍선을 화면 안으로 옮기고 클릭 영역도 같이 바뀝니다.
- **색상:** truecolor에서는 그대로, 256색 터미널에서는 Rich가 색을 낮춰 그립니다. 16색 이하이거나 `NO_COLOR`가 설정되면 픽셀 대신 문자 장면(`[>_ ]`, `[| |]`, `| 작업대 |`)으로 바꿉니다.

| 키 (마당) | 동작 |
| --- | --- |
| `Tab`·`Shift+Tab` | 마당 ↔ 요청함 |
| `←`·`→`·`↑`·`↓` | Codex 펫 → Claude 펫 → 책상 → 말풍선 선택 (노란 모서리와 상태 줄 `선택 ▶`로 표시) |
| `Enter`, 마우스 클릭 | 선택한 대상이나 요청의 상세 열기 |
| `Esc` (상세에서), `y` (상세 콘솔에서) | 마당으로 돌아오기 |
| `c` · `1`–`4` | 상세 콘솔 · 작업/변경 검토/복구/전송 전 점검 탭 바로 열기 |
| `d` | 말풍선 닫기 (읽음 표시, 해결 아님) |
| `m` | 움직임 보통 → 줄이기(걷기·달리기 없음) → 정지 |
| `n` | 데모에서만: 모의 장면 대기 → 시작 → 작업 → 확인 요청 → 검증 통과 → 데모 데이터 |
| `r`, `?`, `q` | 새로고침, 도움말, 종료 (상세 콘솔과 같음) |

데모의 모의 장면은 화면 표현만 바꿉니다. 헤더에 `모의 장면 n/5`가 표시되고 실제 CLI 호출, 검증 실행, 파일 기록은 없습니다. 두 펫은 사용자가 준 참고 이미지를 보고 이 프로젝트에서 작은 도트(Codex 12×12, Claude 14×7)로 다시 그린 것으로, 원본 그림을 그대로 옮긴 것은 아닙니다. 몸 프레임(대기·깜빡임·걷기 2·기쁨·오류)과 소품(화면·키보드·헬멧·망치·생각 말풍선·`?`·`!`·반짝임·빗자루·`z`)은 `console/sprites.py`의 문자열 배열과 팔레트로 바꿀 수 있습니다. 실행할 때 이미지 파일을 읽거나 내려받지 않습니다.

- **변경 검토 (2):** 코드 기준, 기준 버전 대비 변경과 연결되지 않은 변경, 보호 경로, 승인 상태와 차단 사유, 요구사항 추적.
- **복구 (3):** 재개 판단, 마지막 흐름, 작업별 실행 기록(종료 미확인 여부, 마지막 관측 시각, 지금 할 일)과 확인한 뒤 실행할 `handoff` 명령.
- **전송 전 점검 (4):** Orca 연결 전체 내용, 사용량(`미확인`), Worker 전송 판단과 보류 이유, `p`로 실행하는 읽기 전용 점검(Provider, 보낼 작업과 명령, 차단 사유). 보내는 동작은 없습니다.
- **하단:** 실행 중인 검증의 작업·검증 조건·pid·경과 시간·제한 시간, 흐름 단계와 결과 요약, 기록 저장 실패와 복구 안내, 현재 포커스. 실행기가 알려 주는 단계와 요약만 보여 주며 테스트 출력을 실시간으로 흘려보내지 않습니다(실패하면 출력 마지막 부분을 보여 줌).
- 상태는 색 외에 기호와 글자로 구분합니다: `✓ 완료`, `✗ 검증 실패`, `↻ 재확인`, `▸ 준비`, `- 대기`, `! 실행 확인 필요`. 선택한 작업은 `>`로 표시합니다.
- 폭이 100칸보다 좁으면 목록과 상세를 위아래로 놓고, 목록에서 `Enter`를 누르면 상세만 크게 보며 `Esc`로 돌아옵니다. 긴 이름·경로·오류는 목록에서 줄이고 상세에서 줄바꿈해 모두 보여 줍니다.

### 검증·흐름·승인

- `v`와 `s`는 실행 전에 대상 저장소, 작업, 실행할 검증 조건과 명령, 제한 시간, 기록할 파일, 바꾸지 않는 것(작업 정의의 `command`, 다른 결과, 인증 환경변수)을 보여 주고 `y`로 확인해야 실행합니다. 데모, `--results` 없음, 작업 정의 오류, 다른 실행 진행 중, 마지막 조회 실패, 종료 미확인 실행이 있으면 실행하지 않고 이유를 보여 줍니다.
- 이 화면은 기록하는 동작을 한 번에 하나만 실행합니다. 다른 세션과는 기존 작업 잠금(`<결과 파일>.run-<id>.lock`)이 같은 작업의 중복 실행을 막습니다. 키를 여러 번 눌러도 실행은 한 번입니다.
- 검증 결과·흐름 상태·실행 기록·승인 기록은 기존 JSON 형식 그대로 같은 파일에 남으므로 CLI와 섞어 써도 됩니다.
- 최종 승인(`a`)은 화면에 보이는 검토 상태(작업 정의·검증 대상 코드·변경 파일·검증 결과·연결 없는 변경 목록·기존 승인 기록)를 함께 넘깁니다. 기록 직전에 결과 파일 잠금 안에서 모두 다시 읽어 대조하고, 하나라도 바뀌었으면 기록하지 않고 다시 검토하라고 안내합니다. 연결된 작업이 없는 변경은 확인란을 직접 체크해야 하고, 보류(`h`)는 사유를 입력해야 기록됩니다.
- **최종 변경 승인은 Worker 실행 승인이 아닙니다.** 승인해도 Worker 전송 차단 사유(실행 승인 없음, 4-A 미통과 등)는 그대로입니다.
- 화면 이동, 새로고침, 전송 전 점검, 종료는 검증·승인·Worker 실행을 일으키지 않습니다. 조회와 점검은 Orca의 `status`·`run-current`와 읽기 전용 Git 명령만 실행합니다.

### 종료와 복구

- 실행 중인 것이 없으면 `q`로 바로 닫히고 터미널 화면과 입력 모드가 원래대로 돌아옵니다.
- 검증이나 흐름이 실행 중이면 `계속 보기`, `끝나면 닫기`, `중지하고 닫기`를 고릅니다(대화상자에서 `Ctrl+C`를 한 번 더 누르면 `중지하고 닫기`). 중지하면 테스트 프로세스를 끝내지만 그 하위 프로세스까지 끝났는지는 확인하지 않으므로, 시간 초과와 같이 실행 기록에 `실행 상태 확인 필요`(종료 미확인)로 남고 결과는 기록하지 않습니다. 흐름이 검증 사이에 있으면 다음 검증을 시작하지 않고 멈추며, 이때는 종료 미확인이 아닙니다.
- 중지하는 동안 `Ctrl+C`를 한 번 더 누르면 기록을 기다리지 않고 닫습니다. 이 경우와 탭을 닫거나 프로세스가 강제 종료된 경우 실행 기록은 `실행 중`으로 남고 OS가 잠금을 풀어, 다음 조회에서 `실행 상태 확인 필요`로 판정됩니다. SIGTERM·SIGHUP은 `중지하고 닫기`와 같이 처리합니다(macOS·Linux).
- TUI는 종료 확인을 기록하지 않습니다. 복구 탭이 보여 주는 명령(화면을 연 인자 그대로)에 확인한 내용을 적어 직접 실행합니다.

```bash
python -m orca_orchestrator.handoff --tasks plan.json --results results.json --repo . --confirm-stopped T-2 --note '확인한 내용'
```

- 조회가 실패하거나 45초 넘게 끝나지 않으면 이전 결과를 지우지 않되 상단과 각 탭에 `최신이 아님`을 표시하고, 다시 조회할 때까지 기록하는 동작을 막습니다. 늦게 도착한 조회 결과는 버립니다.

### 확인한 범위와 제한

- Textual 헤드리스 테스트(`App.run_test`)로 장면별 표시와 조작을, 실제 가상 터미널(pty)과 VT100 에뮬레이터로 데모와 예제 저장소의 레이아웃, 키 입력, 한글 폭, 크기 변경(120×36 → 80×24), 실제 테스트 프로세스 실행·흐름·승인, 종료 후 터미널 복원(대체 화면, 커서, 마우스, 입력 모드)을 확인했습니다(macOS, Python 3.11, Textual 8.2.8).
- 픽셀 마당은 Textual 헤드리스 테스트(클릭·키·크기 변경·좁은 화면·색상 제한·`NO_COLOR`)와 가상 터미널(pty, 120×34)에서 truecolor(`COLORTERM=truecolor`)·256색(`TERM=xterm-256color`)·16색(`TERM=xterm`)·`NO_COLOR` 각각의 렌더링, `--console`, 모의 장면 전환, `q` 종료 후 대체 화면·마우스 모드 복원을 확인했습니다(macOS, Python 3.11, Textual 8.2.8). 화면 모양은 Textual 스크린샷(SVG)으로 확인했습니다. **실제 Orca 터미널 안에서 마당의 색, 반블록 정렬, 마우스 클릭은 아직 확인하지 않았습니다.** 그 환경의 truecolor 지원과 글꼴·행 간격에 따른 픽셀 비율도 미확인입니다.
- Orca 1.4.268 터미널(macOS)에서 `--once`로 읽기 전용 상태 조회와 `ORCA_CLI_BIN_DIR`로 CLI를 찾는 것을 확인했습니다. Orca 탭 안에서 사람이 TUI를 직접 조작하는 확인은 하지 않았습니다. 1.4.268은 검증 버전(1.4.264)이 아니어서 `미검증 버전`으로 표시됩니다.
- 사용량은 계속 `미확인`입니다. 테스트 출력은 실시간으로 수집하지 않습니다. 실행 기록 저장 경고는 검증 하나·흐름의 각 검증 단위로만 알립니다.

## 상태 화면

같은 셸에서 데모를 열 수 있습니다. 데모는 패키지에 포함된 응답 픽스처를 재생하며 Orca가 꺼져 있어도 동작합니다. 실제 CLI는 호출하지 않고, 화면 제목에 `데모`가 표시됩니다.

```powershell
python -m orca_orchestrator --demo
python -m orca_orchestrator --demo disconnected --once
```

`--demo` 뒤에 `connected`(기본), `disconnected`, `unbound`, `invalid` 중 하나를 붙이면 연결, 연결 끊김, 바인딩 없음, 응답 오류 장면을 볼 수 있습니다. `--once`는 화면을 한 번 출력하고 종료합니다.

`--once --json`은 같은 읽기 전용 조회 결과를 `orca-orchestrator/snapshot@1` JSON 문서 하나로 출력합니다(GUI용 읽기 전용 계약). 텍스트 `--once` 출력은 그대로이고, `--json`은 `--once` 없이 쓰거나 `--plain`·`--console`과 함께 쓰면 오류입니다. 필드·출처 규칙·고정 예시 문서는 [docs/snapshot-v1.md](docs/snapshot-v1.md)에 있습니다.

Snapshot의 `workers.recorded`는 저장된 실행 기록입니다. 실시간 Worker 관측은 미지원이며 `workers.live.availability`는 `not_implemented`입니다.

```bash
python -m orca_orchestrator --demo --demo-results worker --once --json
```

실제 상태는 Orca 터미널 탭에서 옵션 없이 실행합니다. 대화형 터미널에서는 [대화형 TUI](#대화형-tui)가 열리고, 이 절의 읽기 전용 화면은 `--plain`으로 열거나 `--once`·파이프로 출력합니다(Textual이 없을 때도 이 화면이 열립니다). CLI는 `ORCA_CLI_COMMAND`, Windows 기본 설치 경로, Orca 터미널이 넘겨주는 `ORCA_CLI_BIN_DIR`(macOS Orca 1.4.268에서 확인) 순서로 찾고 `PATH`는 찾지 않습니다.

```powershell
python -m orca_orchestrator
```

| 키 | 동작 |
| --- | --- |
| `r` | 다시 조회해 화면을 새로 그립니다. 자동 갱신은 없습니다. |
| `q` | 화면을 닫습니다. Ctrl+C도 같습니다. |
| `↑`·`↓`, PgUp·PgDn, Home·End | 내용이 창보다 길면 제목과 조작키는 고정한 채 나머지를 이동합니다. `j`·`k`, `g`·`G`도 됩니다. |

- 화면은 Orca 명령 중 `status --json`과 바인딩된 터미널의 `orchestration run-current --json`만 실행합니다. 그 밖의 Orca 명령은 실행 전에 거부합니다.
- `--tasks`를 지정하면 `--repo`(기본: 현재 폴더)의 검증 대상 파일을 읽고, 변경 확인에 읽기 전용 Git 명령(`rev-parse`, `diff`, `ls-files`)만 실행합니다. 그 밖의 Git 명령은 실행 전에 거부하며, Git에는 모델 인증 환경변수와 Orca 터미널 바인딩을 넘기지 않습니다.
- Runtime이 꺼졌거나 바인딩이 없으면 하단에 한 줄 안내가 나옵니다. 해석할 수 없는 응답은 `조회 불가`로 표시합니다.
- 사용량은 아직 연동되지 않아 `미확인`으로 표시합니다. 작업 전송은 항상 보류로 표시됩니다.
- `Worker 명령`은 Worker 명령 근거 중 문서·소스로 확인한 항목과 이 호스트에서 실측한 항목의 수입니다. 자세한 내용은 [Worker 전송 전 점검](#worker-전송-전-점검)에 있습니다.
- `재개`와 `마지막 실행`은 실행 기록을 읽어 보여줍니다. 화면은 흐름을 시작하거나 재개하지 않으며, `r`은 파일과 저장소 상태를 다시 읽기만 합니다.
- 화면을 닫으면 이 터미널만 원래 화면으로 돌아갑니다. Orca Runtime, Run, 사용자 세션에는 영향이 없습니다.

직접 정의한 작업은 `--tasks`로, 기록된 검증 결과는 `--results`로, 검토할 저장소는 `--repo`(기본: 현재 폴더)로 지정합니다. 화면에는 파일 이름만 표시하고, `r`을 누르면 파일과 저장소 상태를 다시 읽습니다.

```powershell
python -m orca_orchestrator --tasks plan.json --results results.json --repo .
```

파일 형식은 [`demo_task_plan.json`](src/orca_orchestrator/fixtures/demo_task_plan.json)과 [`demo_results_failed.json`](src/orca_orchestrator/fixtures/demo_results_failed.json)을 참고하세요. 작업 정의에는 요구사항(`id`, `title`, `acceptance`)과 작업(`id`, `title`, `requirements`, `depends_on`, `checks`)이 들어갑니다. 변경 검토에 쓰는 비교 기준 `base`(Git 리비전)와 작업별 `paths`(이 작업이 바꾸는 경로), `protected_paths`(바꾸면 안 되는 경로)는 선택 항목이며 경로는 저장소 루트 기준 `/` 구분 상대 경로입니다. 검증 결과는 작업·검증 조건별 `passed` 또는 `failed`입니다.

- 작업은 모든 검증 조건이 현재 계획에 맞는 `passed`일 때만 `완료`입니다. 하나라도 `failed`면 `검증 실패`이며 완료되지 않습니다.
- 결과에는 검증 당시 검증 조건의 지문(`check_digest`)과 검증한 코드의 지문(`source_digest`)이 함께 기록됩니다. 그 뒤 해당 검증 조건(ID·설명·`command` 문구)이나 검증 대상 파일이 바뀌었거나, 지문이 없는 이전 결과는 현재 상태에 맞는지 판단할 수 없으므로 `재확인`으로 표시하고 완료로 세지 않습니다.
- `다음 작업`은 흐름이 고를 작업과 이유, `흐름`은 마지막 흐름 실행이 멈춘 이유입니다. `코드 기준`, `변경`, `보호 경로`, `최종 승인`은 [로컬 검증부터 승인까지](#로컬-검증부터-승인까지)에서 설명합니다.
- 직접 선행 작업이 모두 완료되면 `준비`, 아니면 `대기`입니다. `대기`에는 실패하거나 아직 검증되지 않은 선행 작업이 사유로 표시됩니다.
- 요구사항은 연결된 작업이 모두 완료되면 `충족`입니다. 연결된 작업이 없거나 미완료 작업이 있으면 `미충족`입니다.
- 중복 ID, 정의되지 않은 요구사항·선행 작업, 순환 의존성, 검증 조건이 없는 작업, 맞지 않는 검증 결과는 오류로 표시하고 상태를 판정하지 않습니다.
- 화면은 검증 명령을 실행하거나 작업을 Worker에 보내지 않습니다. 작업 정의의 `command`는 설명용이며 어디에서도 실행되지 않습니다.

### 로컬 검증 실행

검증은 사용자가 명령으로 직접 실행합니다. 첫 버전은 `unit-tests` 검증 조건 하나만 지원하며, 프로그램에 정해 둔 `python -m unittest discover -s tests`를 저장소 루트에서 셸 없이 한 번 실행합니다. 아래는 같은 셸에서 데모 작업 정의로 확인한 명령입니다.

```powershell
python -m orca_orchestrator.verify --tasks src/orca_orchestrator/fixtures/demo_task_plan.json --results "$env:TEMP\orca-demo-results.json" --task T-1 --check unit-tests
```

```text
실행: T-1/unit-tests → python -m unittest discover -s tests (한 번, 제한 600초)
검증 통과 · T-1/unit-tests · 종료 코드 0 · Ran 254 tests · OK
기록: orca-demo-results.json (다른 결과 0건 보존)
```

결과는 같은 결과 파일을 `--results`로 지정해 상태 화면에서 확인합니다. 화면을 열어 둔 채 검증을 다시 실행했다면 `r`을 눌러 파일을 다시 읽습니다.

```powershell
python -m orca_orchestrator --tasks src/orca_orchestrator/fixtures/demo_task_plan.json --results "$env:TEMP\orca-demo-results.json"
```

```text
작업 목록   2개 · 완료 1 · 준비 1 · demo_task_plan.json · orca-demo-results.json
  T-1  완료       작업 계약 검증 · FR-01 · 검증 1/1 통과
  T-2  준비       요구사항 추적 표시 · FR-07 · 선행 T-1 완료
```

- 지정한 작업과 검증 조건이 작업 정의에 있고, 작업 정의와 기존 결과 파일에 오류가 없을 때만 실행합니다. 그렇지 않으면 아무것도 실행하거나 바꾸지 않습니다.
- 종료 코드 0이면 `passed`, 그 밖이면 `failed`로 기록합니다. 같은 작업·검증 조건의 이전 결과만 바꾸고 다른 결과는 보존합니다.
- 실행 직전에 검증 대상 파일의 지문을 기록하고, 테스트가 도는 동안 그 파일이 바뀌면 어느 코드의 결과인지 알 수 없으므로 기록하지 않습니다.
- 테스트 중에는 결과 파일을 잠그지 않습니다. 저장할 때만 옆의 `<결과 파일>.lock`으로 한 번에 한 프로세스가 최신 파일을 다시 읽고 병합해 교체하므로, 여러 작업을 동시에 검증해도 결과가 모두 남습니다. 최신 파일을 해석할 수 없거나 저장에 실패하면 기존 파일을 그대로 두고 알립니다.
- 제한 시간(`--timeout`, 기본 600초)을 넘기거나, 실행 자체가 실패하거나, 실행된 테스트가 0개이면 결과를 기록하지 않고 원인을 알립니다. 자동으로 다시 실행하지 않습니다.
- 테스트 프로세스에는 Claude·Codex 인증 환경변수와 Orca 터미널 바인딩을 넘기지 않습니다.
- 다른 세션이 같은 작업을 실행 중이거나 그 작업의 이전 실행이 끝났는지 확인되지 않았으면 실행하지 않습니다(`2`). [중단과 이어받기](#중단과-이어받기)를 참고하세요.
- 종료 코드는 통과 `0`, 실패 `1`, 실행 전 거부 `2`, 시간 초과·실행 불가 `3`입니다.

## 로컬 검증부터 승인까지

[`examples/review_project`](examples/review_project)는 계산 함수를 구현하는 작업 `T-1`과 테스트를 쓰는 작업 `T-2`, 두 작업 모두 바꾸면 안 되는 명세 `docs/spec.md`가 있는 작은 저장소입니다. 아래는 이 예제를 임시 폴더에 복사해 **계획 선택 → 로컬 검증 → 변경과 증거 확인 → 사용자 승인 → 변경 후 재확인**을 저장소 루트의 같은 PowerShell에서 따라간 순서입니다. Git이 필요하며 Orca나 모델은 호출하지 않습니다. 시각, 커밋 ID, 지문, 테스트 수는 실행할 때마다 다릅니다.

준비: 기준 커밋 `base`에는 작업 정의와 명세만 넣습니다. `src/`와 `tests/`는 작업 결과로 새로 생긴 변경이 됩니다. `$a`는 이후 명령에 공통으로 넣는 인자입니다.

```powershell
$env:PYTHONPATH = "src;tests"
$demo = "$env:TEMP\orca-review-demo"
Copy-Item -Recurse examples/review_project $demo
git -C $demo init -q -b main
git -C $demo add .gitignore plan.json docs
git -C $demo -c user.name=example -c user.email=example@example.invalid commit -q -m base
git -C $demo tag base
$a = "--tasks", "$demo\plan.json", "--results", "$demo\results.json", "--repo", $demo
```

### 판정 규칙

- **검증한 코드:** 검증 대상은 `--repo` 아래 `src/`와 `tests/`의 파일, 그리고 저장소 루트의 Python 모듈(`*.py`)과 정규 패키지(`__init__.py`가 있는 폴더)이며, 커밋하지 않은 변경도 포함합니다. 단위 테스트는 저장소 루트에서 `python -m`으로 실행되어 루트 모듈을 import할 수 있으므로 루트 모듈도 넣었습니다. 루트 모듈이 없는 저장소의 지문은 이전과 같아 기존 결과가 그대로 유효합니다. `__init__.py`가 없는 폴더(`docs/`, 네임스페이스 패키지)와 `pyproject.toml`·`requirements.txt` 같은 설정·의존성 파일은 지문에 넣지 않습니다. 테스트는 설치된 패키지가 아니라 `src/`에서 불러오기 때문이며, 이런 파일이 바뀌면 변경 파일 지문이 바뀌어 승인은 `재승인 필요`가 됩니다. 결과마다 실행 직전 파일 내용의 지문(`source_digest`)을 기록하고, 현재 파일의 지문과 같을 때만 그 결과를 씁니다. Git `HEAD`와 커밋 전 변경 여부는 표시용이며, `HEAD`가 같아도 파일이 다르면 다른 코드로 봅니다. 캐시(`__pycache__`, `*.pyc`), 숨김 파일·폴더, 작업 정의·결과 파일과 `.lock`·`.flow.json`·`.approval.json`·`.tmp` 파일은 지문에 넣지 않으므로 테스트 실행이나 결과 저장으로 결과가 만료되지 않습니다.
- **이전 결과:** 지문이 없는 이전 결과 파일도 그대로 읽습니다. 다만 어떤 코드를 검증했는지 알 수 없으므로 `재확인`(코드 기준 없는 결과)으로 표시하고, 흐름이 통과 결과를 다시 검증합니다. 이런 결과로는 승인할 수 없습니다.
- **변경 파일:** 작업 정의의 `base` 대비 커밋된 변경, 커밋 전 변경, Git이 무시하지 않는 새 파일을 모읍니다. 각 파일은 `paths`가 덮는 작업에 연결하고, 연결할 작업이 없으면 `확인 필요`로 표시합니다. 작업 정의·결과 파일과 그 부속 파일, 캐시는 목록에서 뺍니다.
- **보호 경로:** 작업의 `protected_paths` 아래 파일이 `base`와 다르면(수정·삭제·추가) 그 작업과 파일을 보여주고 승인을 보류합니다. `base`가 없거나 찾을 수 없거나, `--repo`가 Git 저장소의 최상위 폴더가 아니면 비교 불가로 보류합니다.
- **승인 조건:** 모든 검증 조건이 현재 작업 정의와 현재 코드에 맞는 `passed`이고, 모든 요구사항에 작업이 연결되어 있고, 변경 비교가 되고, 보호 경로가 그대로일 때만 `--approve`가 기록됩니다. 연결할 작업이 없는 변경이 있으면 내용을 확인한 뒤 `--confirm-unlinked`를 함께 줍니다. 기록은 `<결과 파일 이름>.approval.json`에 남습니다.
- **재승인:** 승인 뒤 작업 정의, 검증 대상 코드, 변경 파일 목록이나 내용, `base`가 가리키는 커밋이 바뀌거나 보류 사유가 다시 생기면 `재승인 필요`로 표시합니다.
- **보류:** `python -m orca_orchestrator.review @a --hold "사유"`로 사유와 함께 보류를 기록합니다.
- **자동 승인 없음:** 흐름 완료, 상태 화면의 `r`, 테스트 통과는 승인 기록을 만들거나 바꾸지 않습니다. 승인과 보류는 `review`에 `--approve` 또는 `--hold`를 줄 때, 또는 TUI의 승인·보류 대화상자에서 사용자가 확인할 때만 기록됩니다. TUI 승인은 검토한 화면 상태와 기록 직전 상태가 같을 때만 기록됩니다.
- **종료 코드:** `review`는 승인 가능·승인 기록·보류 기록 `0`, 보류 사유가 있거나 승인을 거부하면 `1`, 작업 정의나 결과 파일을 쓸 수 없으면 `2`입니다.

### 흐름 규칙

- **선택 규칙:** 계획 순서에서 선행 작업이 모두 완료됐고, 자동 실행할 수 있는 검증 조건(`unit-tests`) 중 결과가 없거나 재확인이 필요한 통과 결과가 남은 첫 작업을 고릅니다. 같은 파일과 코드면 항상 같은 작업을 고릅니다.
- **멈추는 경우:** 검증 실패(`1`), 실행 전 거부(`2`), 시간 초과·실행 불가·실행된 테스트 0개·테스트 중 코드 변경·결과 기록 실패(`3`), 더 고를 작업 없음(`4`), `--max-tasks` 도달(`5`)에서 멈춥니다. 다른 세션이 작업을 실행 중이면(`6`), 이전 실행이 끝났는지 확인해야 하면(`7`) 아무것도 시작하지 않습니다. 모든 작업이 끝나면 `0`입니다. 멈춘 작업과 이유를 출력하고 `<결과 파일 이름>.flow.json`에도 남겨 상태 화면에 보여줍니다. 같은 명령을 다시 실행하면 저장된 결과에서 이어갑니다.
- **재실행하지 않는 것:** 흐름은 실패한 검증을 자동으로 다시 실행하지 않습니다. 원인을 고친 뒤 `python -m orca_orchestrator.verify`로 그 검증을 직접 실행하고, 흐름을 다시 실행해 이어갑니다. 작업 정의의 `command` 문자열은 실행하지 않습니다.
- **파일:** 검증 결과는 기존 `--results` 형식으로 저장하며 다른 작업의 결과를 보존합니다. 저장과 승인 기록 때만 `<결과 파일>.lock`으로 잠급니다.
- 흐름이 검증 실패로 멈춘 장면은 `python -m orca_orchestrator --demo --demo-results failed`로 볼 수 있습니다.

### 재개 판단

- **작업별 상태:** `완료`(현재 작업 정의·코드에 유효한 결과, 다시 실행하지 않음), `이어가기 가능`, `재확인 필요`(기록 후 코드·검증 조건·작업 정의가 바뀜), `검증 실패`, `대기`, `진행 불가`(흐름이 자동 실행할 수 없는 검증 조건), `실행 상태 확인 필요`, `다른 세션 실행 중`, `Worker 작업 완료·터미널 정리 중`으로 나눕니다.
- **실행 상태 확인 필요:** 시간 초과로 멈춘 실행, 그리고 `실행 중`으로 기록됐지만 그 세션이 종료 기록 없이 사라진 실행입니다. 확인이 끝날 때까지 흐름과 `verify`는 그 작업을 다시 실행하거나 다른 세션에 넘기지 않고, 다른 작업도 시작하지 않습니다. `handoff --confirm-stopped <작업> --note "확인한 내용"`으로 사용자가 확인을 기록해야 이어갈 수 있습니다.
- **한 작업에 한 세션:** 작업을 실행하는 세션은 `<결과 파일>.run-<8자리>.lock`을 잡고 있습니다. 운영체제는 프로세스가 어떻게 끝나든 이 잠금을 풉니다. 그래서 잠금이 풀린 `실행 중` 기록은 끊긴 세션이고, 잠금이 잡혀 있으면 다른 세션이 실행 중입니다. 다른 세션이 같은 작업을 잡으려 하면 시작하지 않습니다(흐름 종료 코드 `6`).
- **실행 ID:** 로컬 검증은 테스트 프로세스의 `pid`를, Worker 실행은 Orca Dispatch ID를 `dispatch:<id>`로 기록합니다. 확인할 수 없는 실행 ID와 종료 상태는 `미확인`으로 표시합니다. 로컬 프로세스가 아직 도는지는 자동으로 조회하지 않습니다.
- **역할:** 완료 여부는 결과 파일, 사용자 결정은 승인 기록, 마지막 흐름이 한 일은 `.flow.json`, 작업별 시도와 다음 행동은 실행 기록이 맡습니다. 실행 중이거나 확인이 필요한 작업이 있으면 최종 승인도 보류합니다.
- **화면:** 상태 화면과 `handoff`(옵션 없이)는 읽기만 합니다. 실행과 재개는 사용자가 `flow`나 `verify`를 실행할 때만 일어납니다.

### Worker 상태와 복구

Worker 실행도 로컬 검증과 같은 실행 기록과 재개 판단을 씁니다. 상태 판정은 Experiment 4-B에서 관측한 순서에 맞췄고, 아래 동작은 가짜 실행기와 [예시 응답 픽스처](src/orca_orchestrator/fixtures/worker_lifecycle_1.4.264.json)로 검증합니다.

- **기록:** `worker-start` 응답의 `dispatchId`를 실행 ID `dispatch:<id>`로, 보낸 Run을 `orca_run`으로, 응답과 `worker-show`에서 본 상태를 `관측`으로 남깁니다. Orca 출력 원문은 복사하지 않습니다.
- **Dispatch ID:** 형식(접두사·문자 종류)을 가정하지 않습니다. 비어 있지 않고 공백으로 둘러싸이지 않으며 `-`로 시작하지 않는 출력 가능한 문자열이면 받습니다. 대신 `worker-show` 응답이 조회한 Dispatch ID를 그대로 돌려주지 않거나, 다른 Run을 가리키거나, 문자열이어야 할 필드의 타입이 다르면 그 응답 전체를 믿지 않습니다.
- **세 가지 증거:** 작업(Dispatch 정산 상태), 프로세스(liveness), 터미널(`terminalState`)을 따로 봅니다.

  | `worker-show` | 표시 | 재개 판단 |
  | --- | --- | --- |
  | 정산 전 · `live` | 실행 중 | 다시 보내지 않고 다시 조회 |
  | 정산됨 · `live` 또는 터미널이 `released`가 아님 | 작업 완료·터미널 정리 중 | 다시 보내지 않고 정리 후 다시 조회 |
  | 정산됨 · `exited` · `released` | 종료 확인 | 결과 파일로 판단 (다음 세션이 작업을 잡을 수 있음) |
  | 그 밖 (`unverifiable`, 필드 누락, 알 수 없는 값) | 종료 미확인 | 사용자가 확인한 뒤 `--confirm-stopped` |

- **조회 실패:** 시간 초과, 오류, 해석할 수 없는 응답, 다른 Dispatch·Run의 응답이면 `종료 미확인`으로 기록하고 마지막으로 확인된 상태를 함께 남깁니다. 화면에 두 가지가 모두 보입니다. 종료가 확인된 실행은 다시 조회하지 않습니다.
- **작업 검증과 별개:** Orca의 `succeeded`는 Dispatch에 대한 Orca의 보고입니다. 작업의 검증 조건 통과나 최종 승인으로 기록하지 않습니다. 출력에 완료 문구가 있어도 증거로 쓰지 않습니다.
- **다시 보내지 않는 경우:** `worker-start`가 시간 초과·응답 누락·해석할 수 없는 응답·`failed`·`outcome_unknown`·Run 불일치로 끝났거나, 보낸 세션이 끊겼거나, Worker가 실행 중·정리 중이거나 종료가 확인되지 않으면 같은 작업을 다시 보내거나 다른 세션에 넘기지 않습니다. Dispatch가 생기기 전에 거부된 경우(`no_active_sender_terminal` 등)만 시작하지 않은 것으로 봅니다.
- **확인:** `python -m orca_orchestrator.handoff --tasks ... --results ... --observe`가 종료가 확인되지 않은 Worker 실행마다 `worker-show`(읽기 전용)를 한 번 실행해 관측을 기록합니다. 다시 보내거나 중지하지 않습니다. 조회로 종료가 확인되지 않으면 Orca에서 직접 확인한 뒤 `--confirm-stopped`로 기록합니다.

데모로 세 장면을 볼 수 있습니다(예시 값, Orca 호출 없음).

```powershell
python -m orca_orchestrator --demo --demo-results worker-finishing --once   # 작업 완료·터미널 정리 중
python -m orca_orchestrator --demo --demo-results worker-exited --once      # 종료 확인
python -m orca_orchestrator --demo --demo-results worker --once             # 조회 실패 · 마지막 확인 상태 표시
```

가짜 실행기로 `worker-start` 한 번 → `handoff --observe` 네 번(실행 중 → 정리 중 → 정리 중 → 종료 확인)을 거치는 흐름은 `$env:PYTHONPATH = "src;tests"` 뒤 `python -m unittest test_workers.LifecycleTest -v`로 재현합니다. Orca나 모델은 호출하지 않습니다.

`worker-finishing`의 재개 부분입니다. 작업은 끝났지만 터미널이 아직 정리되지 않아 다시 보내지 않습니다.

```text
다음 작업   보류 · T-2 Worker 작업 완료·터미널 정리 중 (재개 참고)
재개        Worker 작업 완료·터미널 정리 중 · T-2 · 실행 ID dispatch:example-di…
마지막 실행 T-2 · 작업 완료·터미널 정리 중 (Orca 조회) · 시작 11-26 20:31:00 · …
  실행 ID dispatch:example-dispatch-4b · 작업 완료·터미널 정리 중
  관측 11-26 20:40:00 · 작업 완료·터미널 정리 중
    작업 succeeded(settled) · 프로세스 live · 터미널 reclaimable
  확인 완료 없음 · 남은 확인 screen-tests
  다음 행동: 정리가 끝나기를 기다린 뒤 handoff --observe로 다시 조회
```

`worker-exited`에서는 종료가 확인되어 실행 기록이 더 이상 재개를 막지 않습니다. Worker의 성공과 별개로 `T-2`는 검증 조건 `screen-tests`의 결과가 없어 `준비` 상태이고(흐름이 자동 실행하지 않는 조건이라 `진행할 수 없음`), 최종 승인도 보류됩니다.

```text
다음 작업   없음 · T-2: 자동 실행할 수 없는 검증 조건 screen-tests
재개        진행할 수 없음 · T-2: 자동 실행할 수 없는 검증 조건 screen-tests
마지막 실행 T-2 · 종료 확인 (Orca 조회) · 시작 11-26 20:31:00 · 세션 s-4d5e6f70
  실행 ID dispatch:example-dispatch-4b · 종료 확인
  관측 11-26 20:44:00 · 종료 확인
    작업 succeeded(settled) · 프로세스 exited · 터미널 released
  확인 완료 없음 · 남은 확인 screen-tests
  다음 행동: T-2: 흐름이 자동 실행하는 검증 조건은 unit-tests뿐임
```

`worker`는 정리 중이던 Worker를 다시 조회하다 실패한 장면입니다. 지금 확인할 수 없는 항목과 마지막으로 확인한 상태가 함께 나옵니다.

```text
다음 작업   보류 · T-2 실행 상태 확인 필요 (재개 참고)
재개        실행 상태 확인 필요 · T-2 · worker 시작됨 (ready · terminal) · 종료…
마지막 실행 T-2 · 종료 미확인 · 시작 11-26 20:31:00 · 세션 s-4d5e6f70
  실행 ID dispatch:example-dispatch-4b · 종료 미확인
  관측 11-26 20:52:00 · 종료 미확인
    worker-show 조회 실패 (outcome_unknown) · 확인 불가: 작업·프로세스·터미널
  마지막 확인 11-26 20:40:00 · 작업 완료·터미널 정리 중
    작업 succeeded(settled) · 프로세스 live · 터미널 reclaimable
  확인 완료 없음 · 남은 확인 screen-tests
  다음 행동: handoff --observe로 상태 조회 · 종료 확인 전 다시 보내지 않음
```

### 4-B 결과와 다음 실환경 시험

Claude 4-B는 승인된 1회 실행을 마쳤고 판정은 `PARTIAL`입니다. Worker의 시작·작업 완료·종료는 확인했고, 실제 구독 인증은 확인하지 못했으며(`UNVERIFIED`), 공식 사용량 표시가 전후 같았다는 것만으로 과금 여부를 판정할 수 없습니다(`INCONCLUSIVE`). 실제 전송 경로는 이 빌드에 없고, 다시 실행하려면 새 승인이 필요합니다. 다음 시험에서 확인할 범위는 [PRD](docs/PRD.md#claude-4-b-실측-반영-phase-1)에 있습니다.

## 구독과 과금

실제 실행을 승인하기 전, 사용자가 공식 Claude Code·Codex CLI에서 자기 구독으로 로그인하고 해당 경로의 **추가 사용과 자동 충전을 꺼 둡니다**. 기본 정책은 구독에 포함된 사용량만 쓰는 것입니다. 프로그램에 한도 도달이 기록되면 리셋을 기다립니다. 초기화 시각이 불명확하면 대기를 유지하고, 시각이 지나면 새 사용량 관측으로 여유를 확인한 후 대기를 해제합니다. API 키로 자동 전환하거나 추가 크레딧을 구매하지 않습니다.

Worker 작업 전송에는 실제 실행 경로의 구독 인증, 구독 외 과금 배제, 해당 자동화 방식에 적용되는 공식 정책 근거 및 별도 사용자 승인이 필요합니다. 현재 Step 0의 4-A는 `CONDITIONAL`입니다. Claude 4-B는 한 번 실행해 `PARTIAL`(Worker 시작·완료·종료 확인, 구독 인증 미확인, 과금 판정 불가)이고, Codex 4-C와 Feasibility Gate는 보류 상태입니다. Provider별로 확보한 근거와 남은 근거는 `preflight`의 `4-A 근거`에 나옵니다.

## 개발 현황

[PRD v0.3](docs/PRD.md)에 현재 구현 경계와 인수 조건을 정리했습니다. `COORDINATOR` 연동을 제품 코드에서 개발하고 로컬 테스트로 검증합니다. 실제 Worker 실행 예시는 해당 경로를 검증하고 별도 승인을 받은 뒤 추가합니다.
